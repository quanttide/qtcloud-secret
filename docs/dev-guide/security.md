# 安全设计：服务端加密实现

> 本文档说明量潮机密云的安全模型——**服务端可信，主密钥（MASTER_KEY）由运维管理**，
> 以及当前架构下的完整安全风险清单与缓解措施。
> 相关文档：[storage.md](./storage.md)（存储选型）、[transfer.md](./transfer.md)（传输架构）、[model.md](./model.md)（数据模型）、[user-guide/master-key.md](../user-guide/master-key.md)（主密钥丢失处置）。

## 1. 架构概述：服务端加密

```
客户端（登录后）──明文──▶ FC 应用服务 ──MASTER_KEY 加密──▶ OSS（密文落盘）
客户端 ◀──明文── FC 应用服务 ◀──MASTER_KEY 解密── OSS
```

- **信任根在服务端**：客户端经 qtcloud-auth 登录（JWT）后直接读写明文
- **加密落盘**：secret 字段由服务端主密钥 `MASTER_KEY`（base64 32 字节，AES-256-GCM）加密
- **双层静态保护**：应用层密文（MASTER_KEY）+ OSS 层 SSE-OSS（OSS 托管密钥）+ 桶私有 ACL
- **运维资产**：主密钥由运维生成/保管/轮换，丢失可重置（恢复路径见 master-key.md），用户零负担

> 历史：本产品最初采用客户端零知识架构（Argon2id 派生 + 密文信封），
> 因单团队内部场景下"主密钥+恢复码双因子"的用户负担远大于收益而放弃（决策记录见 CHANGELOG）。
> 服务端加密是内部系统常见形态（团队密码库/Wiki/网盘同模型）。

## 2. 密钥管理（MASTER_KEY）

### 2.1 密钥层次

```
MASTER_KEY（运维生成：openssl rand -base64 32，GitHub org secret 注入）
   │
   ▼ AES-256-GCM（每条目随机 12 字节 nonce，密文含 GCM 认证标签）
secret 字段（条目内容）
```

- 注入链：GitHub org secret `MASTER_KEY` → CI（TF_VAR_master_key）→ terraform → FC 环境变量
- 每条目独立 nonce：同一条目多次加密产生不同密文
- GCM 认证标签：密文被篡改时解密立即失败

### 2.2 生命周期

```
① 生成：openssl rand -base64 32（不依赖用户）
② 注入：org secret → CI → FC 环境变量（生产必须配置）
③ 使用：加密/解密所有条目的 secret 字段
④ 丢失：密文不可解密 → 用明文备份恢复（见 user-guide/master-key.md）
⑤ 轮换：导出备份 → 换 MASTER_KEY → 清空数据 → 恢复备份（全量重加密）
```

### 2.3 已知边界（密钥可见面）

MASTER_KEY 明文存在于三处，任一处泄露 = 全部条目可解密：

| 位置 | 风险 | 缓解 |
|------|------|------|
| FC 环境变量 | 有 FC 读权限者可查看 | 限制 RAM 权限；日志/控制台访问审计 |
| terraform state（OSS 远程 state 桶） | 明文落盘 | state 桶私有 + SSE 加密；规划 Vault/配置中心迁移 |
| GitHub org secret | 组织管理员可见 | 最小化管理员；密钥轮换制度 |

## 3. 安全风险清单（当前架构）

### 🔴 高风险

**R1. 凭据集中且可见面广**
- `MASTER_KEY` 是**单点**：一个密钥加密所有数据，且明文存在于 FC 环境变量 / tfstate / org secret 三处
- 影响：任一处泄露 = 全部条目可解密；失去"每个用户各自密钥"的隔离
- 缓解：state 桶私有 + SSE；限制 FC/RAM 读权限；轮换制度；中期迁移 Vault（见 §6）

**R2. 默认密钥 fallback（隐蔽后门）**
- 生产若漏配 `JWT_PUBLIC_KEY`，验签回落硬编码默认值 `quanttide-auth-secret`——**知道默认值者可自行签发有效 token 读写全部数据**
- 缓解：**生产环境拒绝 fallback 启动**（config 增加环境校验：`ENV=prod` 且未配置公钥时启动失败）；CI 部署后自动探测验证

**R3. 账号 = 全量数据**
- 任何能登录 qtcloud-auth 的账号都能读写**所有**条目（无细粒度权限）
- 影响：一个账号泄露（弱密码/钓鱼）即数据全泄露
- 缓解：MFA（依赖 auth 侧）；强密码策略；最小化账号数量；未来加团队/成员权限

### 🟠 中风险

**R4. 会话 token 无撤销机制**
- auth 签发 JWT 有效期 7 天，泄露后无法吊销（无黑名单）
- 缓解：缩短有效期；泄露后改密码（防后续登录）；auth 侧加 token 吊销

**R5. 无应用层速率限制**
- 登录接口与 API 均无限流/爆破防护
- 缓解：auth 侧登录限流/验证码；provider 每用户/每 IP 限流

**R6. 审计不足**
- audit 仅为容器 stdout 日志（FC 日志），无独立审计存储、无异常告警（批量导出/异常时间访问）
- 缓解：审计落 OSS/日志服务 + 告警规则

**R7. 备份是明文副本**
- 备份页导出的 NDJSON 是明文（客户端-服务端交互即明文），保管不当 = 数据直接泄露
- 缓解：加密压缩备份；限制导出权限（当前任何登录账号可导出全部）

### 🟡 低风险 / 改进项

**R8. name 明文存储**：条目名称元数据可见（OSS 泄露时）——可接受（列表必需），命名避免敏感字眼

**R9. OSS 版本控制保留历史**：已删条目旧版本保留 30 天（生命周期已配）——恢复窗口与泄露窗口并存

**R10. 客户端明文面**：明文在浏览器可见——XSS/恶意扩展/截屏可窃取；建议剪贴板自动过期、自动锁屏、CSP

**R11. Web 产物逆向**：Flutter Web 可被逆向分析——token 仅内存态（已实践），勿落 localStorage

## 4. 攻击场景推演

| 攻击场景 | 结果 |
|----------|------|
| OSS 桶全量泄露（含凭证） | 拿到 MASTER_KEY 加密的密文；无密钥不可解密；SSE-OSS 再加一道 |
| FC 应用服务被攻破（RCE） | 攻击者可读代码/密文，**但 MASTER_KEY 在环境变量中——可读取后解密全部数据**（服务端加密的核心信任假设：服务端自身可信） |
| FC 环境变量泄露 | 等同 MASTER_KEY 泄露 → 全部数据可解密 |
| tfstate 泄露 | 同上（MASTER_KEY 明文在其中） |
| 账号密码泄露 | 可登录并读写全部条目（R3） |
| 默认密钥后门被利用 | 无 JWT_PUBLIC_KEY 配置时可用默认 secret 签发 token（R2） |

> 服务端加密的诚实边界：**服务端（FC/运维/云厂商）本身可信是前提**——
> 与零知识方案不同，攻破服务端 = 拿到密钥 = 解密全部数据。
> 这是单团队内部系统的可接受假设（团队信任自己的运维），换取用户零负担。

## 5. 与零知识方案的对比

| 维度 | 零知识（已放弃） | 服务端加密（当前） |
|------|------------------|--------------------|
| 密钥持有者 | 每个用户（主密码+恢复码） | 运维（MASTER_KEY） |
| 用户负担 | 高（双因子派生、不能丢） | 无（登录即用） |
| 密钥丢失影响 | 该用户数据不可恢复 | 全部数据不可读（有备份可恢复） |
| 服务端被攻破 | 只有密文 | 全部可解密 |
| 恢复路径 | 恢复码（用户保管） | 明文备份（运维制度化） |
| 适用场景 | 不可信服务端、海量个人用户 | 可信内部系统、单团队 |

## 6. Vault 的定位（服务端密钥底座）

> 领域背景：README 领域边界包含"Vault 等密钥管理服务的接入规范"。
> 新架构下 Vault 的职责**更直接**：MASTER_KEY 正是"服务端密钥"，
> 进 Vault 不违背任何安全边界（服务端加密本就信任服务端）。

| 放 Vault | 理由 |
|----------|------|
| **MASTER_KEY** | 替代 FC 环境变量/tfstate 明文落盘——Vault 托管 + 轮换 + 审计 |
| OSS 访问凭证（阿里云 secret engine 动态 STS） | 短期凭证自动轮换 |
| JWT 验签公钥/共享密钥 | 集中托管 + 轮换 |
| 数据库口令（团队版引入 PG 时） | 动态凭据 |

- 当前阶段：**不落地，仅预留架构位**（单团队、密钥可见面可控）；
  待密钥轮换/多团队/合规需求立项时引入（ECS + Raft + unseal 运维）
- Vault 社区版免费 vs KMS 3.0 实例 2,499 元/月——Vault 是砍掉 KMS 后服务端密钥底座的补位方案

## 7. 建议落地顺序

| 优先级 | 事项 | 对应风险 |
|--------|------|----------|
| 立即 | 确认 state 桶私有 + SSE；生产拒绝 fallback 密钥启动 | R1/R2 |
| 短期 | 审计日志落盘 + 告警；导出权限限制；登录限流 | R6/R7/R5 |
| 中期 | MFA；token 吊销；密钥轮换工具；Vault 引入评估 | R3/R4/R1 |
| 持续 | 剪贴板自动过期、自动锁屏、CSP | R10 |

# 数据模型

> 本文档定义量潮机密云当前阶段（单团队、小数据量、忽略高并发）的数据模型。
> 前置：存储选型见 [storage.md](./storage.md)，传输架构见 [transfer.md](./transfer.md)。

## 1. 设计原则：同一套安全架构，多种数据模型

量潮机密云覆盖密码、证件、密钥与敏感信息等所有需要同一套安全架构处理的机密对象。**安全架构统一，数据模型按对象形态区分**：

| 模型 | 适用对象形态 | 示例 | 状态 |
|------|-------------|------|------|
| **文本信封模型** | 短文本机密 | 口令、API Key、Token、私钥、恢复码 | ✅ 当前实现 |
| **文件模型** | 文件/附件形态机密 | 公司证件、法人身份证、资质证书扫描件 | 🚧 规划中 |
| **字段模型** | 结构化多字段机密 | 证件号 + 发证机关 + 有效期、银行账号 | 🚧 规划中 |

三种模型共享同一套安全架构：客户端零知识加密（AES-256-GCM 密文信封）、OSS 版本控制、双重加密、同步与审计机制。**对象形态不同则数据模型不同，互不混用**：

- **文本信封模型**：一条机密 = 一个信封对象，`encrypted.ciphertext` 为单值密文
- **文件模型**：一条机密 = 信封对象（元数据 + 附件清单）+ 多个附件密文对象（证件扫描件等），附件用独立密钥加密
- **字段模型**：一条机密 = 信封对象，`encrypted.ciphertext` 内为结构化字段集合（可逐字段脱敏展示）

## 2. 设计前提（当前阶段）

| 前提 | 影响 |
|------|------|
| 单团队使用，数据量很小 | 无需保险库/租户维度，扁平存储 |
| 忽略高并发 | 无需乐观锁、冲突裁决、增量同步协议 |
| 用户在另一个子系统 | 本系统不存用户，仅验签对方签发的 token |
| 无附件，只有文本机密 | 每个文本机密一个对象，无附件对象（文件模型引入后扩展） |
| 双重加密（客户端 + OSS SSE-OSS） | 对象内为密文信封，bucket 服务端加密兜底 |

## 3. 模型一：文本信封模型（当前实现）

> 适用：口令、API Key、Token、私钥等**短文本机密**。当前唯一落地模型，结构与行为即现状。

### 3.1 存储布局

```
oss://qtcloud-secret/            # bucket，开启版本控制
  secrets/<id>.json              # 每个机密一个 JSON 信封对象（id = UUID v4）
```

- 对象 key 使用不可预测的 UUID，路径不含明文信息
- 无需 `users/`、`vaults/` 前缀——用户在外系统，单团队无保险库维度
- bucket 开启**版本控制**：误删/误写可随时回滚，兼作恢复保险

### 3.2 对象结构（机密信封）

每个机密一个 JSON 对象，结构为「明文元数据 + 密文负载」信封：

```json
{
  "id": "a1b2c3d4-...",
  "name": "GitHub 登录",
  "createdAt": "2026-01-01T00:00:00Z",
  "updatedAt": "2026-01-01T00:00:00Z",
  "encrypted": {
    "algorithm": "AES-256-GCM",
    "kdf": "Argon2id",
    "kdfSalt": "base64...",
    "nonce": "base64...",
    "ciphertext": "base64..."
  }
}
```

| 字段 | 说明 |
|------|------|
| `id` | UUID v4，与对象 key 一致 |
| `name` | 明文元数据，客户端列表/搜索用（明文仅名称，不含机密内容） |
| `createdAt` / `updatedAt` | 展示与排序用，不参与并发控制 |
| `encrypted.algorithm` | 加密算法，固定 AES-256-GCM |
| `encrypted.kdf` / `kdfSalt` | 密钥派生参数（Argon2id + 随机盐），随密文存储 |
| `encrypted.nonce` | GCM 随机数（12 字节，每次加密重新生成） |
| `encrypted.ciphertext` | 机密内容密文（GCM 认证标签包含在内） |

### 密钥派生（当前阶段简化）

- 密钥 = `Argon2id(主密码, kdfSalt)`，客户端本地派生，服务端与 OSS 均不接触
- 当前为单团队个人模式，**无需非对称密钥对与信封包裹**；字段结构保留，未来上团队版时兼容扩展
- 每次加密随机生成 `nonce` 与 `kdfSalt`，同一条目多次加密产生不同密文

### 3.3 读写规则（无并发控制）

| 操作 | 规则 |
|------|------|
| **创建** | 客户端加密 → PUT `secrets/<uuid>.json` |
| **更新** | 客户端重新加密 → 覆盖写同一 key（OSS 版本控制保留旧版本） |
| **删除** | 直接 `DeleteObject`（生成 delete marker，可恢复） |
| **读取** | GET 对象 → 客户端用派生密钥解密，明文仅在内存 |
| **恢复** | OSS 版本控制回滚任意历史版本 |

- 不做 `If-Match` 条件写：单团队并发冲突概率趋近于零，最后写入生效（LWW）
- 不做墓碑软删除：删除即物理删除，由版本控制兜底恢复
- 不做 changelog/增量同步：同步 = `ListObjects` 全量列出 + 差异拉取，小数据量下瞬时完成

### 3.4 同步流程（客户端主导）

```
① 客户端 ListObjects(prefix=secrets/) 全量列出
② 与本地缓存比对（id + updatedAt）得出新增/变更/删除差异
③ 差异对象批量 GET（密文）→ 本地解密合并；本地有而远端无 → 标记删除
④ 本地明文索引（名称/标签）供列表与搜索，明文不落盘
```

## 4. 模型二：文件模型（规划中，证件为第一类对象）

> 适用：公司证件、法人身份证、资质证书等**以文件形态存在**的机密——内容是无法用一段文本承载的扫描件/照片/PDF，需要附件保存与查看。

### 4.1 存储布局

```
oss://qtcloud-secret/            # bucket，开启版本控制
  documents/<id>.json            # 证件信封对象（元数据 + 附件清单，id = UUID v4）
  attachments/<id>/<fileId>      # 附件密文对象（文件二进制，fileId = UUID v4）
```

- 信封与附件分离：信封小（≤64 KB，与现有传输校验兼容），附件按需拉取，不随全量同步
- 附件对象 key 同样使用不可预测的 UUID，路径不含明文信息

### 4.2 对象结构（证件信封 + 附件对象）

证件信封 JSON：

```json
{
  "id": "a1b2c3d4-...",
  "type": "document",
  "name": "营业执照",
  "expiresAt": "2027-12-31",
  "createdAt": "2026-01-01T00:00:00Z",
  "updatedAt": "2026-01-01T00:00:00Z",
  "encrypted": {
    "algorithm": "AES-256-GCM",
    "kdf": "Argon2id",
    "kdfSalt": "base64...",
    "nonce": "base64...",
    "ciphertext": "base64..."     // 结构化字段密文：证件号、发证机关、备注等
  },
  "attachments": [
    {
      "id": "file-uuid",
      "objectKey": "attachments/<id>/<fileId>",
      "fileName": "营业执照扫描件.pdf",
      "mimeType": "application/pdf",
      "size": 1234567,
      "sha256": "base64...",      // 密文哈希（完整性校验，不泄露明文指纹）
      "wrappedKey": "base64..."   // 附件 DEK 包裹密文（见 4.3）
    }
  ]
}
```

| 字段 | 说明 |
|------|------|
| `type` | 对象类型标识（`document`），客户端按类型渲染；文本模型缺省为 `text` |
| `expiresAt` | 证件有效期（明文元数据，敏感度低，供到期提醒；客户端本地索引可据此提醒） |
| `encrypted.ciphertext` | **结构化字段密文**：证件号、发证机关、备注等（字段模型能力在证件上的落地） |
| `attachments[]` | 附件清单（明文元数据：文件名/类型/大小/密文哈希 + 附件密钥包裹密文） |

附件对象（`attachments/<id>/<fileId>`）：文件二进制密文（AES-256-GCM + 附件 DEK），无外层 JSON 包裹，直接存储密文流。

### 4.3 附件加密：独立 DEK + 主密钥包裹（信封加密预演）

```
每个附件：随机生成附件密钥 DEK（AES-256，CSPRNG）
  → 附件内容用 DEK + 随机 nonce 加密 → attachments/<id>/<fileId>
  → DEK 用主派生密钥（Argon2id 输出）包裹 → wrappedKey 存于信封
读取：GET 信封 → 解出 wrappedKey → 主派生密钥解包得 DEK → GET 附件 → 解密
```

- **收益 1（性能）**：附件可能很大（扫描件数 MB），改主密码 / 重加密信封时**附件本体零重加密**，只需重新包裹 DEK（KB 级）
- **收益 2（演进）**：这就是团队版信封加密的最小预演——团队版把"主派生密钥包裹"换成"成员公钥包裹"（见第 7 节），附件加密链路不变
- **完整性**：附件存 `sha256`（对密文计算，不泄露明文指纹），下载后校验，防传输/存储篡改

### 4.4 读写规则（规划中）

| 操作 | 规则 |
|------|------|
| **创建** | 客户端先上传附件（PUT 附件对象）→ 再 PUT 信封（引用附件 + wrappedKey） |
| **更新** | 元数据变更：重加密信封覆盖写；附件变更：上传新附件对象 + 更新信封附件清单（旧附件版本由 OSS 版本控制保留） |
| **删除** | 删信封 + 删附件对象（delete marker，可恢复） |
| **读取** | GET 信封 → 列表/详情（小对象，秒级）；点开附件才 GET 附件对象（按需拉取） |
| **恢复** | OSS 版本控制回滚信封与附件历史版本 |

### 4.5 同步差异（规划中）

- 全量同步只拉**信封**（小对象），附件**按需 GET**——列表、搜索、到期提醒均不触达附件
- 到期提醒：客户端本地明文索引保存 `expiresAt`，临近到期（如提前 30 天）提醒
- 附件缓存：本地缓存密文附件，命中则免下载；缓存策略由客户端控制

## 5. 模型三：字段模型（规划中）

> 适用：证件号、发证机关、有效期、银行账号等**结构化多字段机密**——单值文本无法表达，需要按字段存储、逐字段展示/复制/脱敏。

### 5.1 对象结构

仍为信封对象（存储与传输与文本模型一致），差异在 `encrypted.ciphertext` 内部：

```json
{
  "id": "a1b2c3d4-...",
  "type": "fields",
  "name": "法人身份证信息",
  "fields": ["certNo", "issuer", "validUntil"],
  "createdAt": "...",
  "updatedAt": "...",
  "encrypted": {
    "algorithm": "AES-256-GCM",
    "kdf": "Argon2id",
    "kdfSalt": "base64...",
    "nonce": "base64...",
    "ciphertext": "base64..."     // 字段集合密文（JSON：{certNo, issuer, validUntil}）
  }
}
```

| 字段 | 说明 |
|------|------|
| `type` | `fields`，客户端按字段表渲染 |
| `fields` | 字段名清单（明文，仅结构不含值——与 `name` 同理，敏感度低；也可整体移入加密负载，代价是失去字段级展示） |
| `encrypted.ciphertext` | 字段值集合密文（JSON 对象），零知识边界与文本模型一致 |

### 5.2 使用规则（规划中）

- **逐字段展示/复制**：客户端解密后按字段渲染，复制单个字段（如只需证件号时不必暴露全部）
- **逐字段脱敏**：列表/审计场景复用 `quanttide-secret-toolkit` 的 `pkg/redact`（保留首尾、中间打码）
- **字段校验**：客户端按字段类型校验（日期格式、长度），服务端不接触值
- **与文件模型的组合**：证件类对象 = 字段模型（`certNo`/`issuer`/`validUntil`）+ 文件模型（扫描件附件），见 4.2 信封结构

## 6. 生命周期与运维

| 项 | 配置 |
|----|------|
| 版本控制 | 开启（恢复保险，覆盖 secrets/ 与 attachments/ 全桶） |
| 生命周期规则 | 保留最近 N 个版本 + 清理超过 X 天的历史版本，防止版本无限膨胀 |
| 服务端加密 | bucket 开启 SSE-OSS 兜底（第二层加密，OSS 托管密钥、免费） |
| 访问控制 | bucket 私有，应用服务通过 STS 临时凭证 / presigned URL 访问 |
| 审计 | 应用服务日志文件记录读写操作（当前阶段不建审计对象） |

## 7. 为团队版预留的扩展位

| 未来需求 | 扩展方式 |
|----------|---------|
| 多保险库 | 信封增加 `vaultId` 字段，客户端索引先行 |
| 多团队/租户隔离 | 对象 key 增加 `{tenantId}/` 前缀，或引入 PG 关系层 |
| 团队共享 | `encrypted` 信封升级为公钥包裹的 DEK（信封加密）；文件模型的附件 `wrappedKey` 已是 DEK 包裹结构，**升级为公钥包裹即可，附件零迁移** |
| 附件直传 | 大附件引入 presigned URL 直传（transfer.md §8 已预留），应用服务只签发凭证 |
| 高并发/多端一致性 | 引入 PG + 乐观锁 + changelog 增量同步，密文对象零迁移 |
